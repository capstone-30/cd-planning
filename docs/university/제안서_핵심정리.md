# 캡스톤디자인 제안서 서식 핵심 정리

출처: [제안서_서식.md](제안서_서식.md)

## 1. 문서의 목적과 핵심

이 문서는 특정 프로젝트의 완성된 제안서가 아니라, 컴퓨터공학부 캡스톤디자인의 **제안서 작성과 단계별 발표를 안내하는 서식**이다. 핵심은 다음 질문에 근거를 갖춰 답하는 데 있다.

> 왜 필요한 프로젝트이며, 기존 기술·서비스보다 무엇을 개선하고, 어떻게 구현하고 검증하며, 누가 언제까지 완성할 것인가?

제안서의 논리는 **기술·시장 배경 → 기존 사례의 한계 → 연구동기 → 제안 기능과 개선전략 → 설계 → 정량적 검증 → 역할과 일정**으로 연결되어야 한다.

원문에 등장하는 AI 수학튜터, 메신저, 기술명, 성능 수치, 데이터 규모, 업무 분담과 일정은 작성 예시다. 실제 프로젝트의 확정 요구사항이나 실적으로 해석하지 않는다. 원문의 작성 지시 역시 이 요약에서는 서식이 요구하는 사항으로 정리했다.

## 3. 특히 중요한 작성 기준

### 개발 범위와 차별성

- 원문은 단독 앱이나 단순 AI 알고리즘 사용만으로 구성된 주제를 허용하지 않는다고 명시한다. 앱은 서버와 연동하고, AI는 추가 데이터 분석과 응용 서비스를 제공하도록 요구한다.
- 게임은 시나리오와 캐릭터 디자인을 첨부한다.
- 기업 연계 프로젝트는 기업이 개발하는 부분을 명확하게 표시한다.
- 주요 기능은 기존 사례에서 발견한 한계와 연결되어야 한다. 기능 목록만으로 개발 필요성을 대신하지 않는다.

### 목표와 검증

- 성능 목표는 정확도, 응답시간, 처리량 등 측정 가능한 수치로 제시한다.
- 각 목표에는 **무엇을, 어떤 환경·자료·절차로 측정할지**를 설명하는 시험구성도와 시험방법이 필요하다.
- 원문의 정확도 99%, 응답시간 1분 등의 수치는 예시이며, 실제 목표는 프로젝트에 맞게 설정한다.

### 설계의 구분

| 설계 | 설명해야 하는 것 |
| --- | --- |
| 서비스 시나리오 | 사용자가 시스템을 이용하면서 어떤 흐름으로 결과를 얻는가? |
| 전체 시스템 구성도 | 하드웨어·소프트웨어 구성요소는 무엇이며 어떻게 연결되는가? |
| 핵심기능 동작 설계 | 가장 어려운 기능을 어떤 세부 모듈·연동 방식·알고리즘으로 구현하는가? |
| 상세설계 | 화면, 데이터 구조·DB·프로토콜·파일 구조, 알고리즘·모델, 데모를 실제로 어떻게 구성하는가? |

AI 모델의 상세설계에는 기본모델, 튜닝방법, 설정 파라미터, 학습데이터 구조를 제시한다. 알고리즘은 의사코드나 순서도로 표현할 수 있다.

## 4. 발표 단계별 준비와 평가

아래 일정은 원문 표기 기준이다. 데모는 ‘27.4’, 최종 데모는 ‘27.6’으로 기재되어 있다.

| 단계 | 발표 자료·준비 | 주요 평가 관점 |
| --- | --- | --- |
| 기획 발표 | PPT 15~20쪽. 배경·동기, 개요, 목표·전략, 개념적 설계, 핵심기능 데모, 일정 등을 설명한다. | 주제의 적합성, 개발 필요성·난이도·분량, 개발방향·설계, 성공가능성, 진도, 발표 준비와 팀워크. |
| 데모 발표 — 2027년 4월 | PPT 20~30쪽. 상세설계, 핵심기능 데모, UX 흐름, 개발 현황과 일정을 준비한다. 원문은 겨울방학 중 준비를 안내한다. | 기술적 완성도, 개발 진도, 시연, 지적사항 반영과 팀워크. |
| 최종 데모 — 2027년 6월 | PPT 20~30쪽. 데모 시연 동영상, 판넬 파일, 샘플자료와 시나리오, 개발 현황·지적사항 반영 내역을 준비한다. | 종합적 완성도, 데모 구성과 진행. 공학대전 전시 후보작 선정도 포함한다. |

상세설계는 원문상 2차 발표 범위이며, 준비된 내용은 1차 발표에도 포함할 수 있다. 핵심기능 데모는 개발 성공 여부를 좌우하는 모델·알고리즘 등을 실제 구현해 보여주는 것이며, UX와 아직 연결되지 않은 상태도 가능하다고 안내한다.

데모는 **약 5분 안에 핵심 가치를 설명할 수 있도록** 설계한다. GPS·주변환경·비전 기능처럼 현장 조건에 영향을 받는 기능은 실습실에서 재현하는 방법까지 준비한다.

## 5. 부록과 제출 전 점검

- **Appendix A — 지적사항·반영사항:** 발표나 재심사에서 받은 지적과 반영 내용을 정리하고, 원문 안내에 따라 목차 뒤에 배치한다.
- **Appendix B — 보완자료:** 지엽적인 설명과 예상 질문에 대한 답변 자료를 배치한다.
- **Appendix C — 상세설계:** 주요 화면·UX 또는 하드웨어 모듈 구성, 필요한 데이터·알고리즘·모델 설계, 데모 설계를 포함한다.

### 점검표

- [ ] 기존 사례 3~5개를 비교하고, 해결할 문제와 개선전략을 연결했는가?
- [ ] 주제의 필요성·차별성·개발 범위와 기대효과가 명확한가?
- [ ] 정량적 목표마다 시험구성도와 시험방법이 있는가?
- [ ] 서비스 흐름, 전체 시스템 구성, 핵심기능 동작을 구분해 설명했는가?
- [ ] 개발 도구, 실제 GitHub 저장소, 최종 산출물을 명시했는가?
- [ ] 담당자·월별 일정·진행률·잔여사항이 설계 및 개발 범위와 일치하는가?
- [ ] 본문의 근거와 참고문헌 번호를 연결했는가?
- [ ] 발표 단계에 맞는 설계·데모·지적사항 반영 자료를 준비했는가?
- [ ] 서식의 예시와 미기입 정보를 실제 프로젝트 내용으로 교체했는가?
